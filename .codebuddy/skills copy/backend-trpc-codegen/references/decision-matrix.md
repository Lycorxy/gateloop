# 6维度评估决策矩阵（详细版）

> 用于 Phase 2 API 设计决策阶段，结合具体需求数据做出量化决策。

---

## 一、并发维度

### 1.1 连接池配置决策

| QPS 级别    | MySQL max_open | MySQL max_idle | Redis pool_size | 说明                 |
| ----------- | -------------- | -------------- | --------------- | -------------------- |
| < 100       | 20             | 5              | 20              | 低流量，最小配置     |
| 100 ~ 500   | 50             | 10             | 50              | 标准流量             |
| 500 ~ 2000  | 100            | 20             | 100             | 中高流量             |
| 2000 ~ 5000 | 200            | 50             | 200             | 高流量               |
| > 5000      | 500+           | 100+           | 300+            | 海量流量，需读写分离 |

### 1.2 协程池限流配置

```
QPS < 500   → 不需要协程池（默认 goroutine 调度即可）
QPS 500~2000 → MaxRoutines = QPS * 2（预留缓冲）
QPS > 2000  → MaxRoutines = QPS * 1.5 + 熔断器保护
```

### 1.3 异步模型选择

| 场景                          | 方案                   | 配置              |
| ----------------------------- | ---------------------- | ----------------- |
| 写后通知（如创建订单→发消息） | Kafka 异步解耦         | Producer 批量发送 |
| 缓存回写                      | goroutine + 新 context | 超时 3s，失败忽略 |
| 日志/审计记录                 | trpc.Go                | 超时 5s           |
| 实时性要求高                  | 同步调用 + 超时控制    | ctx timeout       |

### 1.4 热点 Key 识别与处理

```
识别条件：单 Key QPS > 500 或单 Key 大小 > 100KB

处理策略：
  - 读热点：本地缓存（sync.Map + TTL） → Redis → DB
  - 写热点：队列合并 + 批量写入
  - 大 Key：拆分（如 user:profile:123 拆为 user:basic:123 / user:detail:123）
```

## 二、安全维度

### 2.1 鉴权方案决策

| 场景                    | 方案                 | 实现              |
| ----------------------- | -------------------- | ----------------- |
| 内部 RPC 通信           | 无需鉴权（内网隔离） | —                 |
| 对外 HTTP API           | JWT Token            | Filter 层统一校验 |
| 高安全场景（支付/财务） | JWT + HMAC 签名      | 双重验证          |
| 第三方回调              | API Key + IP 白名单  | Filter 配置化     |

### 2.2 输入校验层级

```
Layer 1: Proto 层校验（ValidationV3）
  - 字段类型、长度、范围
  - 正则模式匹配
  - 枚举值校验

Layer 2: Service 层校验
  - 业务规则校验（如"用户状态必须为激活"）
  - 跨字段校验（如"结束时间 > 开始时间"）

Layer 3: Repo 层防护（SQL 注入）
  - 参数化查询（永远不用字符串拼接）
  - GORM 的 Where("id = ?", id) 自动参数化
```

### 2.3 数据脱敏规则

| 数据类型 | 脱敏方式                    | 脱敏层级           |
| -------- | --------------------------- | ------------------ |
| 手机号   | 138\*\*\*\*5678             | Service 层响应封装 |
| 身份证   | 110****\*\*\*****1234       | Service 层         |
| 银行卡   | \***\* \*\*** \*\*\*\* 5678 | Service 层         |
| 密码     | bcrypt 哈希，永不返回       | Repo 层存储        |
| 邮箱     | u\*\*\*@domain.com          | Service 层         |

### 2.4 SQL 注入防护清单

```
✅ GORM: db.Where("id = ?", userInput)           // 参数化
✅ GORM: db.Where("name LIKE ?", "%"+input+"%")  // 模糊查询也参数化
✅ Raw: db.Raw("SELECT * FROM users WHERE id = ?", id)
❌ db.Where("id = " + userInput)                 // 字符串拼接
❌ db.Raw("SELECT * FROM users WHERE id = " + id) // 字符串拼接
❌ db.Order(userInput)                           // 动态排序需白名单校验
```

## 三、性能维度

### 3.1 序列化方案选择

| 场景           | 序列化           | 压缩                             | 理由                |
| -------------- | ---------------- | -------------------------------- | ------------------- |
| 内部 RPC       | Protobuf         | Snappy（大数据）/ 不压缩（<1KB） | 无 Schema 兼容问题  |
| 对外 HTTP      | JSON             | Gzip                             | 跨语言 + 浏览器兼容 |
| 文件传输       | Protobuf + bytes | Snappy / LZ4                     | 二进制高效          |
| WebSocket 实时 | JSON / MsgPack   | 不压缩                           | 延迟优先            |

### 3.2 缓存策略详细决策

| 查询模式            | 缓存策略         | TTL                     | 更新策略    |
| ------------------- | ---------------- | ----------------------- | ----------- |
| 单条查询（GetByID） | Cache-Aside      | 5~30 min                | 写入时失效  |
| 列表查询（List）    | 不缓存或短 TTL   | 1~3 min                 | 自然过期    |
| 配置/字典           | 启动加载 + TTL   | 1 hour                  | 定时刷新    |
| 热点数据            | 本地缓存 + Redis | 本地 1min / Redis 10min | 两级失效    |
| 计数器              | Redis INCR       | 持久化                  | —           |
| 排行榜              | Redis Sorted Set | 持久化                  | 定时 + 实时 |

### 3.3 批量操作优化

```
批量创建：
  单条 INSERT → VALUES (...), (...) 批量（每批 ≤ 500 条）
  GORM: db.CreateInBatches(records, 500)

批量查询：
  IN 查询 → WHERE id IN (?, ?, ?)（每批 ≤ 200 个）
  Redis: Pipeline 批量 GET

批量删除：
  软删除批量 → UPDATE ... WHERE id IN (...) 单条 SQL
```

### 3.4 索引覆盖率检查

```
关键查询的 EXPLAIN 检查清单：
□ type 列是否为 const / eq_ref / ref / range（不能是 ALL）
□ Extra 列是否出现 Using filesort / Using temporary
□ key_len 是否合理（联合索引使用了几列）
□ rows 扫描行数是否远小于总行数
```

## 四、稳定性维度

### 4.1 超时配置决策

| 层级       | 配置位置               | 建议值 | 依据               |
| ---------- | ---------------------- | ------ | ------------------ |
| 服务端     | server.service.timeout | 1000ms | 80% 请求在此时间内 |
| 客户端调用 | context.WithTimeout    | 500ms  | 内部调用应更快     |
| DB 查询    | context.WithTimeout    | 200ms  | 单条查询应极快     |
| Redis 操作 | context.WithTimeout    | 100ms  | 缓存应更快         |
| Kafka 发送 | context.WithTimeout    | 3s     | 异步可稍长         |

### 4.2 熔断器配置

```
启用条件：下游依赖 > 2 个 或 下游 P99 > 500ms

Google Breaker 参数：
  - window: 10s（统计窗口）
  - bucket: 10（10 个桶，每个 1s）
  - requestVolumeThreshold: 20（最少请求数才触发统计）
  - errorPercentThreshold: 50（错误率阈值）

状态转换：
  Closed ──错误率>50%──→ Open（拒绝所有请求）
  Open ──冷却时间到──→ HalfOpen（允许少量探测）
  HalfOpen ──成功──→ Closed（恢复正常）
  HalfOpen ──失败──→ Open（重新熔断）
```

### 4.3 优雅关闭配置

```yaml
server:
    close_wait_time: 1000 # 等待存量请求完成（ms）
    max_close_wait_time: 3000 # 最大等待时间（ms）
```

```
关闭流程：
1. 收到 SIGTERM
2. 停止接收新请求（健康检查返回不健康）
3. 等待 close_wait_time（让存量请求完成）
4. 超时则强制关闭（max_close_wait_time）
5. 释放连接池、刷日志
```

### 4.4 健康检查端点

```
GET /healthz        → 200 OK（进程存活）
GET /ready          → 200 OK 或 503（DB/Redis 可连接）
GET /metrics        → Prometheus 指标
GET /debug/pprof/   → 性能分析（生产建议绑定 127.0.0.1）
```

## 五、扩展性维度

### 5.1 无状态设计检查

```
□ Service 层不存储请求级变量
□ Logic 层不依赖全局状态
□ 所有状态存储在 DB/Redis 中
□ 可通过增加实例数量水平扩展
□ 不依赖本地文件系统（除非有持久卷）
```

### 5.2 Proto 向后兼容检查

```
✅ 安全变更：
  - 新增 optional 字段（新编号）
  - 新增 RPC Method
  - 新增 Enum Value

⚠️ 需协调：
  - 新增 required 字段
  - 修改字段 default 值

❌ 禁止：
  - 删除/重命名字段
  - 更改字段编号
  - 更改字段类型
```

### 5.3 分库分表预留

```
如果 Phase 3 判定 L4/L5，需预留：
□ 分片键字段（如 tenant_id / user_id）
□ 全局 ID 生成器（雪花算法）
□ 路由层抽象（为未来 ShardingSphere 做准备）
□ 读写分离数据源切换能力
```

## 六、服务器成本维度

### 6.1 资源估算公式

```
内存估算：
  Go 进程基础：~50MB
  goroutine：每个 ~2KB × 预估并发数
  连接池：每个 MySQL 连接 ~2MB × max_open
  缓存：本地缓存大小（手动估算）

CPU 估算：
  QPS × 单请求 CPU 时间（通常 1-10ms）
  例：1000 QPS × 5ms = 5000ms/s = 5 核

带宽估算：
  QPS × 平均响应大小
  例：1000 QPS × 50KB = 50MB/s
```

### 6.2 降成本策略

| 策略       | 效果              | 适用条件       |
| ---------- | ----------------- | -------------- |
| 连接池复用 | 减少 ~30% 内存    | 所有场景       |
| 序列化压缩 | 减少 ~60% 带宽    | 响应 > 10KB 时 |
| 缓存       | 减少 ~80% DB 查询 | 读多写少       |
| 协程池限流 | 防止内存暴涨      | 高并发场景     |
| 零分配设计 | 减少 GC 压力      | 性能敏感路径   |
| 合并部署   | 减少实例数        | 低流量多服务   |
