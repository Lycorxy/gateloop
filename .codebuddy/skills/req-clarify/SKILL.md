# 需求分析 v3.0

**核心定位：基于项目现状分析需求，补齐漏洞，给出最优方案。不是追问用户，而是读代码、读知识库、读记忆，用现有信息补全需求。**

> 🧠 **设计哲学**：需求分析不是"问用户要什么"，而是"基于项目现状发现用户没想到的"。
> 用户给的是目标，分析师的职责是用现有代码/知识/方案，把目标变成完整、可执行、无漏洞的规格。

核心目标：**需求完整 > 功能完善 > 边界充分 > 数据正确 > 布局合理 > 交互丝滑 > 体验优秀**

> 以上目标要**综合交叉考虑**：功能×数据=数据闭合、功能×边界=边界完整……8维度+12交叉验证，确保无盲区。

## Step 1 — 上下文探测 [中自由度 · 强制]

> **不是问用户，而是读项目。** 基于代码、知识库、记忆理解项目现状，为后续分析提供事实依据。

### 🔒 数据契约声明

本步骤需要两个契约（详见 `skill.config.yaml` → `step-contracts`）：

| 契约 ID | criticality | 内容 | on-missing |
|---------|-------------|------|------------|
| project-context | required | 项目代码上下文（技术栈/路由/模型/组件/API/helpers/规范） | block |
| historical-decisions | preferred | 同类需求历史决策与踩坑 | degrade |

## Step 2 — 需求解析 [中自由度 · 强制]

> **将用户需求拆解为技术维度。** 不是问用户"你要什么"，而是基于需求和项目现状，分析出完整的技术维度。

### 2.1 八维度解析

每个需求必须从以下 8 个维度拆解，且维度之间要交叉验证（见 2.3）：

| 维度 | 分析内容 | 依据 |
|------|---------|------|
| **功能点** | 包含哪些功能？输入/输出？能否复用现有组件？ | 需求 + 项目现状 |
| **数据流转** | 数据从哪来→处理→存哪→展示哪？ | 现有数据模型 + API |
| **接口设计** | 需要哪些接口？已有能否复用？新增哪些？ | 现有 API 层 |
| **交互流程** | 操作路径？每步状态变化？反馈？ | 现有组件 + 交互模式 |
| **布局结构** | 页面结构？列表/表单/看板/详情？ | 现有页面模式 + 设计规范 |
| **路由规划** | 新增路由？嵌套关系？权限？懒加载？ | 现有路由结构 |
| **边界条件** | 空数据/超大数据/并发/权限/网络异常？ | 现有错误处理模式 |
| **用户体验** | 学习成本？操作效率？视觉一致性？ | 现有交互模式 + 设计规范 |

> 每个维度的详细分析方法与检查项，参见 `references/analysis-checklist.md`。

### 2.2 解析输出格式

```
📐 需求解析：[需求名称]

功能点：
  1. {功能名} — 输入:{x} → 输出:{y} — 复用:{已有组件/函数}
数据流转：
  {数据源} → {处理} → {存储} → {展示} | 复用:{store/API} | 新增:{...}
接口设计：
  复用:{已有接口} | 新增:{接口} — 方法:{GET/POST} — 入参:{x} — 出参:{y}
交互流程：
  Step1: {操作} → {状态变化} → {UI反馈}
布局结构：
  页面类型:{列表/表单/看板/详情} | 复用:{现有布局组件}
路由规划：
  新增:{path} → {组件} — 权限:{角色} | 嵌套:{父>子}
边界条件：
  □ 空数据→{处理} □ 超大→{分页/虚拟滚动} □ 并发→{乐观锁} □ 权限→{提示} □ 异常→{重试}
用户体验：
  学习成本:{X分钟} | 操作效率:{高频X步} | 视觉一致性:{遵循规范}
```

### 2.3 维度交叉验证矩阵（强制）

8 个维度必须交叉检查，12 组交叉逐项验证。完整矩阵见 `references/analysis-checklist.md` → 维度交叉验证矩阵。

交叉验证输出格式：
```
🔗 交叉验证结果：
功能×数据: ✅闭合/⚠️{问题}/❌{断裂}    功能×接口: ✅覆盖/⚠️{问题}/❌{缺失}
功能×边界: ✅完整/⚠️{问题}/❌{遗漏}    功能×体验: ✅高效/⚠️{问题}/❌{过长}
数据×接口: ✅匹配/⚠️{问题}/❌{断裂}    数据×边界: ✅健壮/⚠️{问题}/❌{异常}
交互×布局: ✅支撑/⚠️{问题}/❌{缺失}    交互×体验: ✅流畅/⚠️{问题}/❌{反馈缺失}
布局×路由: ✅匹配/⚠️{问题}/❌{错误}    路由×边界: ✅安全/⚠️{问题}/❌{漏洞}
路由×体验: ✅流畅/⚠️{问题}/❌{异常}    边界×体验: ✅友好/⚠️{问题}/❌{不友好}
```

> **验证检查点：**
> ```
> □ 8个维度均已分析（含用户体验）
> □ 每个维度都基于项目现状（非猜测）
> □ 12组交叉验证全部完成
> □ 复用项已标注来源 | □ 边界条件已覆盖5类
> ```
>
> 完成播报：`"✅ Step 2 需求解析完成：{N}功能点/{N}接口/{N}路由/8维度+12交叉全覆盖"`

## Step 3 — 差距分析 [中自由度 · 强制]

> **对比需求 vs 现有代码，找出用户没想到的漏洞，判断需求是否正确。** 这是需求分析的核心价值——用户给了目标，分析师负责发现盲区、纠正偏差、补齐缺失。

### 3.1 需求合理性判断（强制 · 先于差距检测）

基于代码事实和项目现状，判断需求方向是否正确。8 维度合理性判断表与输出格式，参见 `references/gap-analysis-matrix.md` → 需求合理性判断。

### 3.2 差距检测矩阵

10 类差距逐项检测：功能缺失/数据断裂/接口缺失/状态管理缺失/权限漏洞/边界遗漏/交互缺失/体验缺失/样式规范缺失/路由冲突。

完整检测矩阵与漏洞示例，参见 `references/gap-analysis-matrix.md` → 差距检测矩阵。

### 3.3 差距报告输出

按 `references/gap-analysis-matrix.md` → 差距报告输出格式 产出。每个差距必须有补齐建议。

> **验证检查点：**
> ```
> □ 8维度需求合理性判断已完成
> □ 10类差距均已检测（含体验缺失）
> □ 每个差距都有补齐建议
> □ 差距基于代码事实（非猜测）| □ 影响等级已标注
> ```
>
> 完成播报：`"✅ Step 3 差距分析完成：合理性{N}✅/{N}⚠️/{N}❌ / 差距{N}项"`

## Step 4 — 方案补齐 [高自由度 · 强制]

> **利用现有知识/方案，给出最优补齐。** 不是让用户自己想，而是分析师基于项目现状直接给出可执行的方案。

### 4.1 补齐原则

```
优先级1：复用现有 — 已有组件/函数/API能复用的优先复用
优先级2：最小改动 — 补齐方案对现有代码影响最小
优先级3：规范一致 — 补齐内容遵循项目现有设计规范
优先级4：体验完整 — 交互/状态/边界全部覆盖
```

### 4.2 补齐方案输出

```
💡 方案补齐

【功能补齐】方案:{复用X组件+新增Y函数} 改动:{N文件} 理由:{...}
【数据补齐】方案:{后端加字段X/前端transform} 复用:{现有transform模式}
【接口补齐】方案:{新增接口} 入参:{x} 出参:{y} 复用:{现有API封装模式}
【边界补齐】空数据:{Empty+CTA} 超大:{分页+虚拟滚动} 并发:{乐观锁} 权限:{守卫} 异常:{ErrorBoundary}
【交互补齐】Loading:{Skeleton} Success:{message+刷新} Error:{message+详情}
【布局补齐】方案:{搜索卡+表格卡} 规范:{卡片三件套+表格对齐}
【路由补齐】方案:{新增path→组件} 嵌套:{父Outlet} 权限:{角色A可访问}
```

### 4.3 优先级排序

```
🔴 Must Have（必须有）：{功能项} — 理由: {没有则不可用}
🟡 Should Have（应该有）：{功能项} — 理由: {重要但可延后}
🟢 Could Have（可以有）：{功能项} — 理由: {锦上添花}
⚪ Won't Have（不做）：{功能项} — 理由: {明确排除}
```

> **验证检查点：**
> ```
> □ 每个差距都有对应补齐方案 | □ 复用项已标注来源
> □ 改动影响已评估 | □ MoSCoW 优先级已排序
> ```
>
> 完成播报：`"✅ Step 4 方案补齐完成：{N}项补齐/复用{N}个/M:{N} S:{N} C:{N} W:{N}"`

## Step 5 — 需求规格输出 [低自由度 · 强制]

### 5.1 产出需求分析文档

使用 `references/output-template.md` 中的模板输出完整需求规格文档。

文档必须包含：
1. **需求概述** — 一句话描述 + 目标用户 + 当前痛点
2. **项目现状** — 技术栈/路由/数据模型/组件/API 盘点
3. **功能规格** — 功能点清单 + 数据流转图 + 接口设计
4. **交互规格** — 操作流程 + 页面布局 + 路由规划
5. **差距与补齐** — 差距报告 + 补齐方案 + 复用清单
6. **边界规格** — 空数据/超大数据/并发/权限/异常 处理方案
7. **优先级** — MoSCoW 分类
8. **验收标准** — 可测试的具体条件（禁止"体验好""性能快"等模糊词）

### 5.2 验证清单

```
□ 需求描述可被不了解背景的人看懂
□ 所有分析基于代码事实（非猜测）
□ 8个技术维度全覆盖（功能/数据/接口/交互/布局/路由/边界/体验）
□ 差距分析已检测10类漏洞
□ 每个差距都有可执行的补齐方案
□ 复用项已标注来源（现有组件/函数/API）
□ 边界条件覆盖5类（空/超大/并发/权限/异常）
□ 验收标准具体可测试
□ MoSCoW 优先级有决策理由
□ 核心逻辑零 MCP 工具名（MCP 调用仅在契约获取子流程）
```

> 完成播报：`"✅ Step 5 需求规格输出完成：文档已产出 / {N}/{10} 项验证通过"`

## 反模式清单

| 反模式 | 正确做法 |
|--------|---------|
| 凭空猜测用户需求 | 读代码/知识库/记忆，基于事实分析 |
| 反复追问用户"你要什么" | 基于项目现状直接给出方案建议 |
| 只分析功能点不分析数据流 | 8维度全面解析 |
| 忽略现有组件硬写新代码 | 优先复用现有组件/函数/API |
| 不检测边界条件 | 10类差距检测必做 |
| 用户没提就不补 | 主动发现漏洞并补齐 |
| 验收标准用模糊词 | 具体可测试（"操作<3秒"非"体验好"） |
| 不考虑路由冲突 | Step 3 差距分析必检 |
| ❸ 核心逻辑里直接调 MCP | MCP 调用仅在契约获取子流程 |

## 错误处理

| 错误场景 | 处理方式 |
|---------|---------|
| 项目无代码（全新项目） | 基于知识库和最佳实践分析，标记"无现有代码参考" |
| 知识库不存在 | 用通用最佳实践替代，标记"无项目知识库" |
| 需求过于庞大 | 拆分为子需求域，逐个分析 |
| 后端接口未就绪 | 标记为前置依赖，前端方案基于接口契约设计 |
| 用户需求与现有架构冲突 | 标注冲突点，给出两种方案（适配现有/重构） |
| ❸ MCP 不可用（project-context 契约） | 降级内置工具探测；全失败则 block 阻断 |
| ❸ MCP 不可用（historical-decisions 契约） | 降级本地 references 兜底继续 |
