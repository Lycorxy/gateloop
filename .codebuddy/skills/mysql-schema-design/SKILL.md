# MySQL Schema Design — 表结构设计专家

## 🛑 入口守卫

```
本 Skill 加载后必须按 Step 0 + Phase 1→...→6 顺序执行全部阶段。
每步播报完成消息，未播报 = 未执行 = 违规。
禁止跳步，禁止跳过 Step 0 规则注入（specflow-rules-engine）。
```

**核心定位：不是"生成建表 SQL"，而是"基于业务场景和数据特征的专业设计决策"。**

> 🧠 **设计哲学**：像一个资深 DBA 那样逐步推理，每一步都有充分的规则约束和验证，
> 而不是拍脑袋给答案。关键决策点必须先注入规则、确认上下文、再行动。

核心目标排序：**业务正确 > 性能最优 > 扩展预留 > 维护便捷**

---

## 何时使用 / 何时不使用

**应该触发：**

- "帮我设计一张用户表"
- "这个订单表要支持千万级数据"
- "新建表的 schema 怎么设计"
- "这个字段应该用什么类型"
- "是否需要分库分表"
- "现有表能不能复用"

**不应触发：**

- 纯 SQL 编写（无设计决策）
- 查询优化 / 慢 SQL 排查
- 数据库运维（备份/恢复/迁移脚本执行）
- Redis / MongoDB / ES 等非 MySQL 设计

## Phase 1 — 需求收集 [中自由度]

在开始设计前，必须明确以下信息。缺失时主动追问：

### 1.1 必须收集（缺一不可）

```
□ 业务实体：这张表存什么？（如"用户信息"、"订单记录"、"操作日志"）
□ 核心字段：有哪些必选字段？各自的含义和约束？
□ 关键查询：最频繁的查询模式是什么？（WHERE 条件 + ORDER + LIMIT）
□ 数据规模：预估总行数？日增行数？
□ 并发特征：读 QPS？写 QPS？读写比例？
□ 一致性要求：（强一致 / 最终一致 / 允许丢失）
```

### 1.2 建议收集（有则更优）

```
□ 是否有现有表可参考或复用？（列出相关表名）
□ 业务是否有状态机/审批流等复杂流转？
□ 是否涉及金额/财务数据？（精度要求）
□ 是否有多租户需求？（隔离级别）
□ 预留扩展方向？（未来可能的功能点）
```

> 🔒 **强制约束**：未完成 1.1 全部项，不得进入 Phase 2。
>
> **跳过必须声明**：
>
> ```
> ⏭️ [跳过] Phase 1 必填项：{跳过的项目名}

> 默认值/假设：{使用了什么默认值或假设代替}
> 风险：{可能造成的设计缺陷}
> ```

## Phase 2 — 复用判定 [高自由度]

> **核心差异点**：专业判断是新建表还是复用/扩展现有表，而非无脑建新表。

### 2.1 判定流程

```
Step A: 扫描现有表结构（search_content / read_file 已有的 .sql 文件）

Step B: 按 RULE.mdc 铁律 0 Phase 2 的判定矩阵逐一评估匹配度
  判定维度：字段重叠度 / 查询模式差异 / 业务域归属 / 访问模式差异 / 数据生命周期 / 安全隔离要求
  灰色地带（重叠 50%~80%）→ 看核心字段重叠度，仍无法判断 → 默认新建

Step C: 输出判定结论 + 理由
```

### 2.2 判定结论示例

| 场景                 | 判定                    | 理由                           |
| -------------------- | ----------------------- | ------------------------------ |
| 用户表加会员等级字段 | **复用**（ALTER TABLE） | 同实体同生命周期，字段重叠≥90% |
| 订单表 vs 退货单     | **新建**                | 状态机不同、生命周期不同       |
| 配置表加新配置项     | **复用**（INSERT）      | K-V 结构天然支持扩展           |

### 2.3 输出格式

```
━━━ 判定结果 ━━━

【结论】：✅ 建议新建表 / ⚠️ 建议复用已有表 {table_name}

【理由】：
1. 字段重叠度：XX%（列出匹配/不匹配字段）
2. 查询模式：{分析}
3. 业务域：{分析}

【操作方案】：
- 新建 → 进入 Phase 3
- 复用 → 给出具体 ALTER / INSERT 方案
```

> 🔒 **强制约束**：此步骤不可跳过。若因特殊原因需跳过，必须输出跳过声明。

## Phase 3 — 规模分级与架构决策 [中自由度]

> **根据 Phase 1 收集的数据规模和并发量，决定表的设计等级。**
> 详细分级标准参见 RULE.mdc 铁律 5。

### 3.1 规模分级速查

| 等级        | 数据量        | 写 QPS     | 设计策略              |
| ----------- | ------------- | ---------- | --------------------- |
| **L1-轻量** | < 10 万       | < 10       | 标准单表              |
| **L2-标准** | 10 ~ 100 万   | 10 ~ 100   | 标准单表+合理索引     |
| **L3-中载** | 100 ~ 500 万  | 100 ~ 500  | 优化单表+读写分离准备 |
| **L4-重载** | 500 ~ 2000 万 | 500 ~ 2000 | 分区表 or 垂直拆分    |
| **L5-海量** | > 2000 万     | > 2000     | 水平分表(+分库)       |

### 3.2 架构决策要点

```
< 100 万 ─────────→ L1/L2 标准单表设计
100~500万 ────────→ L3 中载 → 关注：索引质量 / 归档机制
500~2000万 ───────→ L4 重载 → 关注：分区表 / 垂直拆分 / 只读从库
> 2000万 ─────────→ L5 海量 → 关注：分片键 / 迁移方案 / 全局ID
  → L4/L5 详细策略参见 references/sharding-strategy.md
```

> 🔒 **强制约束**：此步骤涉及关键架构决策，不可跳过。若需跳过，必须输出跳过声明。

## Phase 4 — DDL 设计 [低自由度]

> **此步骤自由度最低**，严格受铁律 1-4 约束。所有命名、类型、索引决策都必须符合铁律。

### 4.1 设计依据（引用铁律）

```
命名规范    → 铁律 2：库名/表名/字段名/索引名规范
必备字段    → 铁律 1：id / created_by / updated_by / create_time / update_time / is_deleted
字段类型    → 铁律 3：主键/金额/布尔/枚举/手机号/身份证/IP/时间/文本/JSON 决策树
索引设计    → 铁律 4：数量 ≤ 6 / 最左前缀 / 覆盖索引 / 禁止项
```

### 4.2 模板选择

根据表类型从 `references/ddl-templates.md` 选择最接近的模板：

| 表类型       | 模板编号 | 适用场景                       |
| ------------ | -------- | ------------------------------ |
| 核心业务实体 | TPL-001  | 用户、商品、文章等主表         |
| 一对多从表   | TPL-002  | 订单明细、评论、附件           |
| 字典/配置    | TPL-003  | 系统参数、数据字典             |
| 日志/审计    | TPL-004  | 操作日志、登录日志（只写不改） |
| 树形结构     | TPL-005  | 组织架构、菜单、分类           |
| 状态机       | TPL-006  | 工单、审批实例、订单           |
| 流转记录     | TPL-007  | 配套状态机的变更历史           |
| 多对多中间   | TPL-008  | 角色-权限、标签-文章           |

> 🔒 **强制约束**：DDL 设计步骤不可跳过。若需跳过，必须输出跳过声明。

## Phase 5 — 设计评审清单 [低自由度]

> **输出 DDL 后逐条检查**，检查项参见 RULE.mdc 铁律 6（共 22 条）。
> 发现违规必须回退修正。

### 5.1 评审要点速查

```
□ 字符集/引擎：InnoDB + utf8mb4 + 无混用
□ 主键：BIGINT AUTO_INCREMENT / 雪花算法
□ 字段：NOT NULL + DEFAULT + COMMENT / 无 ENUM / 无 FLOAT 金额
□ 审计字段：create_time + update_time + is_deleted
□ 索引：≤ 6 个 / uk_/idx_ 命名 / 最左前缀 / 无冗余
□ 架构一致：与 Phase 2 判定 + Phase 3 分级一致
```

> 🔒 **强制约束**：设计评审步骤不可跳过。若需跳过，必须输出跳过声明。

## 错误处理

> 详细规则参见铁律 7。

| 错误场景                 | 处理方式                                     |
| ------------------------ | -------------------------------------------- |
| 用户无法提供数据规模估算 | 给出各等级典型场景供选择，按最高等级保守设计 |
| 字段需求模糊             | 列出该类实体的标准字段模板供勾选             |
| 现有表结构不可获取       | 基于通用经验给出建议，标注"需确认现有表"     |
| 多种设计方案可行         | 给出 2 种方案对比，推荐一种                  |
