### 序列化选型决策树（详细）

```
请求类型？
├── 内部 RPC 调用
│   ├── 高频小消息 (<10KB)        → Protobuf + 不压缩
│   ├── 中频中等消息 (10KB~1MB)    → Protobuf + Snappy
│   └── 低频大消息 (>1MB)          → Protobuf + Gzip
├── 对外 HTTP API

    ├── 低延迟优先                  → MessagePack + 不压缩
    └── 兼容性优先                  → JSON + 不压缩
```

## 二、缓存架构决策

### 2.1 缓存层级选型

```
Level 1: 本地缓存（应用内存）
  适用：热点配置、字典数据（< 1000 条）
  工具：sync.Map / go-cache / bigcache
  TTL：1~10 min
  更新：定时刷新 + Pub/Sub 失效通知

Level 2: Redis 缓存（分布式）
  适用：用户数据、业务实体、Session
  工具：trpc-database/goredis
  TTL：5~30 min
  更新：Cache-Aside / Write-Through

Level 3: 数据库（兜底）
  始终作为最终数据源
```

### 2.2 缓存更新策略对比

| 策略              | 读取路径             | 写入路径          | 适用场景       | 风险           |
| ----------------- | -------------------- | ----------------- | -------------- | -------------- |
| **Cache-Aside**   | 查缓存→空则查DB→回写 | 更新DB→失效缓存   | 读多写少       | 缓存不一致窗口 |
| **Read-Through**  | 缓存层自动查DB       | —                 | 封装好的缓存层 | 首次加载慢     |
| **Write-Through** | —                    | 同步写缓存+DB     | 强一致性需求   | 写入延迟       |
| **Write-Behind**  | —                    | 先写缓存→异步写DB | 高写入吞吐     | 数据丢失风险   |

### 2.3 缓存 Key 设计规范

```
格式：{service}:{entity}:{identifier}:{version}

示例：
  user:profile:12345:v1
  order:detail:ORD-2024-001:v1
  product:hot:list:v2
  session:web:abc123def456
  lock:order:create:user_123
  rate:api:login:192.168.1.100

反例：
  user_123          ← 无命名空间
  cache:user:123    ← 太通用
  u:p:123           ← 缩写不明确
```

### 2.4 缓存穿透/击穿/雪崩防护

| 问题     | 现象                        | 解决方案              | 配置         |
| -------- | --------------------------- | --------------------- | ------------ |
| **穿透** | 查不存在的Key，每次都打到DB | 布隆过滤器 + 空值缓存 | 空值 TTL 60s |
| **击穿** | 热点Key过期，大量并发查DB   | 互斥锁 + 逻辑过期     | 锁超时 3s    |
| **雪崩** | 大量Key同时过期             | TTL 加随机偏移        | ±20% 随机    |

```go
// 击穿防护：单飞模式（singleflight）
var g singleflight.Group

func (l *Logic) GetWithProtection(ctx context.Context, id int64) (*Entity, error) {
    key := fmt.Sprintf("entity:%d", id)
    val, err, _ := g.Do(key, func() (interface{}, error) {
        // 只有一个 goroutine 会真正查 DB
        return l.repo.FindByID(ctx, id)
    })
    return val.(*Entity), err
}
```

## 三、消息队列选型

### 3.1 Kafka vs RabbitMQ vs NATS

| 特性          | Kafka                  | RabbitMQ  | NATS                 |
| ------------- | ---------------------- | --------- | -------------------- |
| 吞吐量        | ⭐⭐⭐⭐⭐             | ⭐⭐⭐    | ⭐⭐⭐⭐             |
| 延迟          | ⭐⭐⭐                 | ⭐⭐⭐⭐  | ⭐⭐⭐⭐⭐           |
| 消息持久化    | ✅ 默认                | ✅ 支持   | ⚠️ JetStream         |
| 消息回溯      | ✅                     | ❌        | ⚠️ JetStream         |
| 顺序保证      | 分区内有序             | ❌        | ❌                   |
| 运维复杂度    | ⭐⭐⭐                 | ⭐⭐      | ⭐                   |
| tRPC 原生支持 | ✅ trpc-database/kafka | ❌ 需封装 | ✅ go-clean-template |

### 3.2 消息队列使用决策

```
场景判断：
├── 事件溯源 / 大数据管道 / 日志收集  → Kafka
├── 任务队列 / 延迟消息 / 复杂路由    → RabbitMQ
├── 低延迟实时通信 / 云原生微服务     → NATS
└── 简单异步解耦（< 1000 QPS）       → Redis Pub/Sub 或 不引入
```

### 3.3 Kafka Topic 设计

```
命名：{domain}.{entity}.{event}.{version}

示例：
  order.created.v1
  order.paid.v1
  user.registered.v1
  inventory.deducted.v1
  notification.email.sent.v1

分区数 = max(生产速率 / 单分区吞吐, 消费并发数)
  单分区吞吐：~10MB/s 或 ~10000 msg/s
  建议分区数 = max(3, QPS/5000)
```

## 四、数据库连接池调优

### 4.1 MySQL 连接池公式

```
max_open = (QPS × 平均查询耗时) × 1.5
max_idle = max_open × 0.2（至少 10）
max_lifetime = 180s（默认，防止长连接内存泄漏）
conn_max_idle_time = 60s（回收空闲连接）

示例计算：
  QPS=500, 平均查询耗时=10ms
  max_open = 500 × 0.01 × 1.5 = 7.5 → 取 20（最小值）
  max_idle = 10
```

### 4.2 Redis 连接池公式

```
pool_size = QPS × 平均耗时 × 1.2 / 1000

示例计算：
  QPS=1000, 平均耗时=2ms
  pool_size = 1000 × 2 × 1.2 / 1000 = 2.4 → 取 20（最小值）
```

## 六、压缩算法选型

| 算法       | 压缩率 | 速度 | CPU 开销 | 适用场景        |
| ---------- | ------ | ---- | -------- | --------------- |
| **不压缩** | 1:1    | 最快 | 0        | 数据 < 1KB      |
| **Snappy** | 1:2~3  | 快   | 低       | 内部 RPC 大数据 |
| **LZ4**    | 1:2~3  | 极快 | 极低     | 实时流 / 日志   |
| **Gzip**   | 1:4~6  | 慢   | 高       | 对外 HTTP API   |
| **Zstd**   | 1:4~8  | 中   | 中       | 归档 / 冷数据   |
