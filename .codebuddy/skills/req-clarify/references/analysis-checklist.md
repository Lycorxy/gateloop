# 需求分析维度清单

> Step 2 需求解析时使用。7 个维度逐项分析，确保需求完整。

---

## 维度 1：功能点

```
分析方法：
  1. 从需求描述中提取所有动词（用户要做什么操作）
  2. 每个操作对应一个功能点
  3. 定义每个功能点的输入/输出
  4. 标注可复用的现有组件/函数

输出格式：
  功能点N: {名称}
    输入: {用户输入/数据来源}
    输出: {结果/状态变化}
    复用: {现有组件/函数名} 或 新增
```

## 维度 2：数据流转

```
分析方法：
  1. 画出数据流向：数据源 → 处理 → 存储 → 展示
  2. 标注每步的数据格式
  3. 检查与现有数据模型的衔接
  4. 标注需要新增的 store / API

检查项：
  □ 数据从哪来？（后端API / 用户输入 / 本地存储）
  □ 数据怎么处理？（transform / 过滤 / 排序）
  □ 数据存到哪？（Zustand store / localStorage / URL参数）
  □ 数据展示在哪？（表格 / 表单 / 图表）
  □ 现有数据模型能否复用？
```

## 维度 3：接口设计

```
分析方法：
  1. 列出需求需要的所有接口
  2. 对比现有API层，标注复用/新增
  3. 定义新接口的方法/入参/出参
  4. 检查接口权限要求

检查项：
  □ 增删改查各需要哪些接口？
  □ 现有接口能否复用？
  □ 需要新增哪些接口？
  □ 接口权限角色是什么？
  □ 是否需要批量操作接口？
```

## 维度 4：交互流程

```
分析方法：
  1. 画出用户操作路径（Step1 → Step2 → Step3）
  2. 标注每步的UI状态变化
  3. 标注每步的反馈（loading/success/error）
  4. 检查与现有交互模式的一致性

检查项：
  □ 用户从哪进入？（导航/按钮/URL）
  □ 每步操作后有什么反馈？
  □ 操作成功后去哪？
  □ 操作失败后怎么恢复？
  □ 是否需要二次确认？（删除等危险操作）
```

## 维度 5：布局结构

```
分析方法：
  1. 判定页面类型（列表/表单/看板/详情/设置）
  2. 参考现有同类页面布局
  3. 标注页面区域划分
  4. 检查设计规范一致性

页面类型决策：
  列表管理 → 搜索卡片 + 表格卡片
  表单编辑 → 字段≤6 Modal / 7-15 Drawer / >15 独立页
  数据看板 → 统计卡片行 + 图表区
  设置页   → 分组卡片 + 底部操作栏
  树形分栏 → 左树240px + 右侧flex:1
```

## 维度 6：路由规划

```
分析方法：
  1. 确定新增路由的path
  2. 确定路由嵌套关系（Outlet）
  3. 确定路由权限控制
  4. 检查与现有路由的冲突

检查项：
  □ 新路由path是否与已有路由冲突？
  □ 嵌套关系是否合理？
  □ 权限控制如何配置？
  □ 是否需要路由懒加载？
  □ 路由参数设计（/detail/:id 还是 query ?id=）
```

## 维度 7：边界条件

```
必须覆盖5类：
  □ 空数据    → 列表无数据时展示空态+CTA
  □ 超大数据  → >500条分页或虚拟滚动
  □ 并发操作  → 多人同时编辑的冲突处理
  □ 权限不足  → 无权限提示或重定向
  □ 网络异常  → 请求失败的重试和兜底

额外检查：
  □ 输入边界（最大长度/特殊字符/空值）
  □ 状态边界（未登录/token过期/角色变更）
  □ 时间边界（跨天/跨月/时区）
```

## 维度 8：用户体验

```
分析方法：
  1. 从用户视角走一遍完整操作路径
  2. 评估学习成本和操作效率
  3. 检查视觉一致性和错误恢复
  4. 对比现有同类功能的体验水平

检查项：
  □ 新用户能否在5分钟内完成首次操作？
  □ 高频操作是否≤3步完成？
  □ 视觉风格是否与现有页面一致？
  □ 操作失败后用户能否快速恢复？
  □ 是否有键盘导航支持？
  □ 等待时间>1秒的操作是否有loading反馈？
  □ 是否有操作引导/提示文案？
  □ 危险操作是否有二次确认？
```

---

## 维度交叉验证矩阵

> 8个维度不是孤立的，以下12组交叉必须逐项验证。

### 功能 × 数据
```
□ 每个功能点的数据来源是否明确？
□ 功能输出数据是否被其他功能消费？
□ 数据链路是否闭合（无断裂）？
```

### 功能 × 接口
```
□ 每个功能点是否有对应接口支撑？
□ 接口返回字段是否满足功能需要？
□ 增删改查功能是否都有对应接口？
```

### 功能 × 边界
```
□ 每个功能点的5类边界是否都考虑了？
□ 空数据时功能是否可用？
□ 超大数据时功能是否正常？
```

### 功能 × 体验
```
□ 高频功能的操作路径是否最短？
□ 低频功能是否可发现？
□ 功能入口是否明显？
```

### 数据 × 接口
```
□ 接口返回字段 vs 前端数据模型是否匹配？
□ 有无字段断裂（前端需要但后端不返回）？
□ 数据类型是否一致（后端string vs 前端number）？
```

### 数据 × 边界
```
□ 空数据时数据流转是否正常？
□ 超大数据时分页/虚拟滚动是否影响数据流？
□ 网络异常时数据状态是否可恢复？
```

### 交互 × 布局
```
□ 交互流程的每步在布局上是否有对应区域？
□ 操作按钮位置是否符合布局规范？
□ 弹窗/抽屉的尺寸是否匹配布局？
```

### 交互 × 体验
```
□ 每步操作的反馈是否符合用户预期？
□ 等待时间是否可接受（<1秒即时反馈，>1秒loading）？
□ 操作可撤销吗？错误可恢复吗？
```

### 布局 × 路由
```
□ 每个布局对应的路由是否正确？
□ 嵌套路由的布局关系是否匹配？
□ 路由参数在布局中是否正确使用？
```

### 路由 × 边界
```
□ 无权限访问路由时的处理？
□ 路由参数缺失/非法时的处理？
□ 路由跳转失败时的兜底？
```

### 路由 × 体验
```
□ 路由跳转是否流畅（无白屏）？
□ 浏览器返回行为是否符合预期？
□ 路由切换时数据是否需要保留？
```

### 边界 × 体验
```
□ 边界场景下的用户体验是否可接受？
□ 错误提示是否友好（非技术堆栈）？
□ 空数据/错误页是否有引导文案和CTA？
```
