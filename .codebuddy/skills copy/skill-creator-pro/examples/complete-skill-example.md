# 完整 Skill 示例：code-review-check

一个展示所有最佳实践的生产级 skill。

## 文件：SKILL.md

```markdown
---
name: code-review-check
description: >
  执行彻底的代码评审，检查 bug、安全漏洞、
  命名违规和性能问题。当用户请求
  代码评审、review code、code review、检查 bug、查找问题、
  优化现有代码或检查 PR 变更时使用。
  不要用于编写新功能、回答语法问题、
  生成样板代码或评审非代码文档。
version: 1.0.0
dependencies: []
conflict-with: []
allowed-tools: [read_file, search_content]
max-token: 2000
---

# 代码评审检查器

自动识别现有源文件中的 bug、安全问题和代码质量问题。

## 何时使用
- 用户要求"评审"、"检查"、"审查"现有代码
- 用户提到 代码评审、查bug、代码优化、review代码
- 用户分享文件/PR 并询问问题或改进
- 用户询问隐藏 bug 或潜在问题

## 何时不使用
- 用户要求编写或创建新代码或功能
- 用户询问语法问题（"怎么写 for 循环？"）
- 用户要求架构设计或技术选型
- 目标不是源代码文件

## 评审工作流

复制此清单并跟踪进度：

```
评审进度：
- [ ] 阶段 1：读取并映射所有目标文件
- [ ] 阶段 2：安全审计（注入、鉴权、密钥）
- [ ] 阶段 3：逻辑检查（边界情况、竞态条件、null 处理）
- [ ] 阶段 4：质量检查（命名、结构、重复）
- [ ] 阶段 5：输出优先级报告
```

### 阶段 1：读取并映射

1. 完整读取所有目标文件
2. 映射文件之间的导入/依赖关系
3. 识别核心逻辑流
4. 注意文件大小和复杂性指标

**如果未指定文件**，询问用户要评审哪个文件。不得猜测。

### 阶段 2：安全审计 [高优先级]

检查每个文件：

| 检查项 | 要查找的内容 |
|-------|------------|
| 注入 | SQL/NoSQL/命令/HTML 注入向量 |
| 密钥 | 源代码中硬编码的密钥、令牌 |
| 鉴权 | 敏感端点缺失鉴权 |
| XSS | 响应中未转义的用户输入 |
| SSRF | 用户提供的 URL 传递给 fetch/request |
| 路径遍历 | 从用户输入构造的文件路径 |

**对于每个发现，记录：** 文件、行号、严重程度（CRITICAL/HIGH/MEDIUM/LOW）、描述、修复建议。

### 阶段 3：逻辑检查 [中优先级]

| 检查项 | 要查找的内容 |
|-------|------------|
| Null/undefined | 变量在未做 null 防护的情况下使用 |
| 差一错误 | 循环边界、数组索引 |
| 异步错误 | 缺失 await、未处理的 promise 拒绝 |
| 资源泄漏 | 未关闭的文件/连接/句柄 |
| 错误吞掉 | 空 catch 块、静默失败 |
| 类型强制 | 意外类型比较（== vs ===） |

### 阶段 4：质量检查 [低优先级]

| 检查项 | 要查找的内容 |
|-------|------------|
| 命名 | 函数/变量描述其用途 |
| 重复 | 相同逻辑复制 3+ 次 |
| 复杂性 | 函数 >50 行，嵌套 >4 层 |
| 死代码 | 不可达分支、未使用导入 |
| 注释 | 对非明显逻辑缺失解释 |

### 阶段 5：输出报告

始终使用此格式：

## 代码评审报告

**已评审文件：** [列表]
**问题总数：** X（严重: X，高: X，中: X，低: X）

### 严重问题（立即修复）

**1. [文件]:[行号] — [问题标题]**
- 严重程度：CRITICAL
- 描述：[什么问题以及为什么危险]
- 建议：[具体代码修复]

### 高优先级

[同格式]

### 中优先级

[同格式]

### 低优先级（建议）

[同格式]

### 总结

[2-3 句话：整体评估，首要操作项]

## 错误处理

- **文件未找到**：报告错误，询问用户正确路径。不得用猜测重试。
- **文件过大（>1000 行）**：分块评审，在输出中标注块边界。
- **非代码文件**：说明文件类型不受支持，如适用建议转换。
- **未发现问题**：仍输出报告格式，显示"问题总数：0"和正面总结。

## 验证

在交付报告之前：
- [ ] 每个问题都有具体行号
- [ ] 每个问题都有具体修复建议
- [ ] 问题按严重程度排序（CRITICAL 优先）
- [ ] 无假阳性（重新读取可疑行以确认）
- [ ] 总结与详细发现匹配

## 参考资料

每个检查类别的详细规则：[references/check-rules.md](references/check-rules.md)
```

## 文件：skill.config.yaml

```yaml
priority: 85
auto-trigger: true
trigger-keywords:
  - 代码评审
  - review code
  - code review
  - check for bugs
  - 查bug
  - 代码优化
  - optimize existing code
depends-on: []
mutual-exclude: []
require-tools: [read_file, search_content]
load-strategy: lazy
unload-after-run: true
max-duration: 180
trigger-weight:
  代码评审: 95
  review code: 90
  "check for bugs": 85
  查bug: 80
  代码优化: 60
```

## 文件：examples/triggers.json

```json
{
  "should_trigger": [
    "帮我review一下这个文件有没有问题",
    "检查这段代码有没有隐藏bug",
    "review src/auth/login.ts",
    "这个PR有什么问题吗？",
    "优化一下这段代码的写法"
  ],
  "should_not_trigger": [
    "帮我写一个登录接口",
    "JS for循环语法怎么用",
    "创建一个新的React组件",
    "用什么数据库比较好？",
    "解释一下闭包是什么"
  ]
}
```

## 本示例的关键要点

1. **Description**：3 部分结构，含中文 AND 英文确切触发关键词
2. **工作流**：agent 可复制并跟踪的清单格式
3. **自由度等级混合**：安全审计 = 中（结构化检查），质量检查 = 高（启发式判断）
4. **输出格式**：带强制章节的严格模板
5. **错误处理**：每类错误的具体恢复操作
6. **验证**：交付前清单防止假阳性
7. **Config**：触发权重反映置信水平（明确"review" > 模糊"optimize"）
