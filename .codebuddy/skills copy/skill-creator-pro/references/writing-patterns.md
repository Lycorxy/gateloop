## Description：3 部分公式

每个 description 必须包含三个部分：

```
[功能描述，第三人称]。当 [触发关键词] 时使用。不要用于 [反触发场景]。
```

### 正确示例

**代码评审：**
> "执行代码评审，检查 bug、安全问题。当用户请求 代码评审、review code、检查 bug、优化现有代码时使用。不要用于编写新功能、回答语法问题。"

**版本管理器：**
> "管理 AI 对话代码版本，支持快照和回滚。当用户说 保存版本、查看历史、回滚代码、对比版本时使用。不要用于 git 操作或 lint 修复。"

### 反模式

| 错误示例 | 问题 |
|---------|------|
| "帮助写代码" | 无触发词，无边界 |
| "我可以帮你评审代码" | 第一人称（破坏注入） |
| "一个处理文档的 skill" | 太模糊，无操作清晰度 |

## 输出格式模板

### 严格模板（需要确定性输出）

```markdown
始终使用此确切格式：

## [章节标题]
[具体结构 — 不得偏离]

## [章节标题]
[具体结构 — 不得偏离]
```

**适用于：** API 响应、数据转换、可解析报告。

### 灵活模板（agent 判断可提高质量）

```markdown
以下为合理默认。根据上下文调整：

## [章节标题]
[建议结构 — 按需调整]

## [章节标题]
[建议结构 — 按需调整]
```

**适用于：** 分析报告、建议、自适应输出。

## 决策树

用于有分支逻辑的工作流：

```
需要操作？
├── 条件 A → 步骤 X（确切命令）
├── 条件 B → 步骤 Y（带参数）
└── 都不满足 → 步骤 Z（默认路径）
```

**规则：**
- 每个分支都以具体步骤结束
- 无死胡同（每条路径都有结果）
- 最常见路径在前
- 嵌套最多 2 层深度

## Skill 正文清单

每个 SKILL.md 正文必须包含：

- [ ] **概述**：1-2 句话（做什么 + 为什么）
- [ ] **何时使用**：触发条件列表，含关键词
- [ ] **何时不使用**：反触发词列表
- [ ] **工作流**：编号祈使句步骤（非散文段落）
- [ ] **自由度等级标注**：如混合使用，每步标注 [低]/[中]/[高]
- [ ] **输出格式**：模板，标明严格/灵活
- [ ] **错误处理**：每类错误的显式恢复（非泛化的"处理错误"）
- [ ] **验证清单**：agent 必须通过的交付前检查
- [ ] **参考资料**：懒加载文件链接（仅一层深度）

### 正文长度预算

| 组件 | 建议行数 |
|------|---------|
| 概述 + 边界 | 15-20 |
| 工作流步骤 | 30-80 |
| 输出格式模板 | 10-20 |
| 错误处理 | 10-20 |
| 验证 | 5-10 |
| 参考资料链接 | 5-10 |
| **总目标** | **<200**（为领域逻辑留空间） |

如果领域逻辑导致正文 > 500 行 → 立即卸载到 references/。
