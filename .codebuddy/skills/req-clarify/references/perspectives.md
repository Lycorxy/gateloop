# 多视角审视框架

从多个维度审视同一个需求，每个视角都会暴露不同的问题。强制至少使用 3 个视角，**安全视角为必选**。

## 视角清单

### 👤 用户视角

**核心问题：用户真正要完成什么任务？**

```
必答题：
- 用户现在怎么完成这个任务的？（当前工作流）
- 当前方案最大的 3 个痛点是什么？
- 这个功能每天/每周/每月用几次？
- 新用户需要多长时间学会？
- 老用户会因为什么原因放弃？

反模式：
- 假设用户和技术人员一样理解系统
- 忽略用户的替代方案（Excel、纸质、口头沟通都是竞品）
- 把"用户说想要"等同于"用户需要"
```

### 💼 业务视角

**核心问题：做这个功能对业务有什么价值？**

```
必答题：
- 不做这个功能会损失什么？
- 做了能带来什么可量化的收益？（收入/留存/NPS）
- 与当前季度/年度的战略目标有什么关系？
- 竞品有这个功能吗？他们做得怎么样？
- 如果只能做一个功能，是这个吗？

反模式：
- 用"老板说要做"代替价值论证
- "竞品有所以我们也要有" — 跟随不是策略
- 忽略机会成本 — 做 A 意味着不做 B
```

### 🔧 技术视角

**核心问题：技术上可行吗？代价多大？**

```
必答题：
- 核心能力依赖什么技术？是否成熟？
- 需要修改哪些现有模块？影响范围多大？
- 是否需要引入新技术栈或第三方服务？
- 预估开发工作量？（人天）
- 是否有技术债务需要先偿还？

反模式：
- 低估集成复杂度
- 追求技术完美而非业务价值
- 用新技术"练手"
```

### 🎨 体验视角

**核心问题：用户会在哪个时刻感受到价值？**

```
必答题：
- 用户从打开到完成目标的路径是什么？
- 最关键的那个操作步骤是什么？（关键时刻）
- 什么情况下用户会感到困惑或沮丧？
- 首次使用的用户的体验和熟练用户有何不同？
- 错误发生时用户看到什么？能自行恢复吗？

反模式：
- 只考虑理想情况下的体验
- 忽略加载/等待/错误状态的体验
- 把"功能多"等同于"体验好"
```

### 📊 数据视角

**核心问题：需要什么数据？数据从哪里来？**

```
必答题：
- 核心数据从哪里获取？（已有数据库/外部API/用户输入）
- 数据质量如何？是否有缺失/不一致？
- 需要实时数据还是可以接受延迟？
- 数据量有多大？增长趋势如何？
- 数据是否有合规要求？（GDPR/个人信息保护法）

反模式：
- 假设数据存在且准确
- 忽略数据清洗和ETL工作量
- 不考虑数据权限和脱敏
```

### 🔒 安全视角（必选）

**核心问题：如何保护用户和系统？**

```
必答题：
- 谁可以访问这个功能？（角色/权限）
- 数据是否有敏感信息？需要脱敏/加密吗？
- 输入是否有注入攻击风险？是否做了校验？
- 操作是否有审计日志？
- 是否有频率限制/防刷机制？

反模式：
- "内部系统不需要安全" — 内部威胁 > 外部威胁
- "后面再加安全" — 安全是设计约束，不是事后补丁
- 只关注功能权限，忽略数据权限
```

## 使用指南

1. 至少使用 3 个视角，安全视角必选
2. 每个视角至少回答 3 个必答题
3. 标注每个视角发现的关键风险
4. 如果某个视角不适用，声明理由后跳过

## 视角选择决策树

```
需求类型是什么？
├── 用户直接使用的功能 → 用户视角 + 体验视角 + 安全视角
├── 后台管理功能 → 用户视角 + 安全视角 + 数据视角
├── 数据处理/报表 → 数据视角 + 技术视角 + 业务视角
├── 系统集成/API → 技术视角 + 安全视角 + 数据视角
└── 不确定 → 至少 用户+安全+业务 三个视角
```
