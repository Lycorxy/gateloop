# 需求澄清与分析 v1.2

**核心定位：像一个资深产品架构师那样，将模糊想法转化为可执行的清晰需求。**

> 🧠 **设计哲学**：需求澄清不是一次性问答，而是一个结构化的对话过程。
> 先发散（探索所有可能性）→ 再收敛（聚焦核心价值）→ 最后输出（可执行文档）。
> 每一步都有强制检查点，不通过不进入下一步。

核心目标排序：**暴露假设 > 明确边界 > 价值验证 > 可执行性 > 文档完整**

## 🛑 入口守卫

```
本 Skill 被 use_skill 加载后，必须按顺序执行 Step 0→1→2→3→4→5 全部步骤。
每步必须播报对应完成消息。未播报的步骤 = 未执行 = 违规。

禁止行为：
  ✗ 跳过 Step 0 直接分析需求
  ✗ 不播报完成消息（无日志 = 没走流程）
  ✗ 无声跳过任何步骤

唯一例外：同会话已执行并播报过的步骤可跳过，但必须声明：
  ⏭️ [跳过] Step N — 理由 | 风险
```

## 何时使用 / 何时不使用

**应该触发：**

- "帮我梳理一下这个需求"、"分析一下这个功能"
- "用户说要做一个XXX，帮我理清思路"
- "这个 PRD 有什么问题？"、"需求评审"
- "我想做一个XXX但不确定怎么做"
- 任何模糊、碎片化、需要澄清的需求描述

**不应触发：**

- 纯技术方案设计（如"这个接口怎么设计"）
- 已有完整 PRD 需要直接开发（→ node-backend-codegen / frontend-codegen）
- 单行修改或明确的 bug 修复
- 纯代码层面的讨论

## 中断与恢复机制

若执行过程被中断（如模型输出截断、用户切换上下文），重新继续时必须：

1. **扫描已有输出** — 检查已完成的 Step 及其完成播报
2. **播报恢复点** — 使用标准格式：
   ```
   ⏯️ [恢复] 上次进度：X/Y 步完成
   已完成：✅ Step 0 — 规则注入
           ✅ Step 1 — 需求捕获
           ✅ Step 2 — 发散展开
           ✅ Step 3 — 评估收敛
           ✅ Step 4 — 优先级排序
           ✅ Step 5 — 交付验证
   待完成：⬜ Step N — {待完成步骤}
   断点：从 Step N 继续
   ```
3. **从断点继续** — 不重复已完成步骤，不遗漏未完成步骤
4. **重启确认** — 播报恢复后主动询问用户是否继续

> **注意**：若已播报过的 Step 上下文丢失（如模型重置），应先提示用户可能需要补充部分信息再继续。

## Step 1 — 需求捕获 [高自由度 · 强制]

> **先完整理解，再分析和评判。不要急于给方案。**
>
> 自由度说明：需求捕获是开放式的探索过程，问题顺序和追问深度可根据对话自然调整。

### 1.1 收集原始需求

向用户收集以下信息，缺失项主动追问：

```
□ 一句话描述：这个需求要解决什么问题？
□ 目标用户：谁会使用这个功能？（角色、场景）
□ 触发场景：用户在什么情况下需要这个功能？
□ 期望结果：使用后用户得到了什么？（成功的定义）
□ 当前方案：用户现在怎么解决这个问题的？（竞品/手工）
□ 约束条件：时间、资源、技术栈限制？
□ 关联系统：依赖哪些已有系统或功能？
```

### 1.2 需求健康度初判

在收集阶段就标记以下信号：

| 信号             | 含义             | 行动                    |
| ---------------- | ---------------- | ----------------------- |
| "所有人都会用"   | 目标用户不明确   | 追问具体角色            |
| "就像XXX那样"    | 可能只是竞品模仿 | 追问差异化需求          |
| "先做出来看看"   | 缺少成功标准     | 追问验收指标            |
| "这个很简单"     | 可能低估复杂度   | 不急于反驳，进入 Step 2 |
| 需求描述不断变化 | 核心问题未定义   | 回溯到"一句话描述"      |

> 完成播报：`"✅ Step 1 需求捕获完成：已收集 {N}/{7} 项信息"` — 收集 ≥5 项才可进入 Step 2。
>
> **验证检查点：**
> ```
> □ 已收集 ≥5 项原始需求信息
> □ 已标记需求健康度信号（如有）
> □ 已确认未急于给方案，仅做收集与标记
> ```

## Step 2 — 发散展开 [高自由度 · 强制]

> **用多个视角审视同一个需求，暴露盲区。这是质量的分水岭。**
>
> 自由度说明：发散阶段没有固定路径，根据需求特点选择 5Why / 多视角 / 场景穷举的顺序和深度，但 3 个工具都至少使用一次。

### 2.1 5Why 追溯法

对需求连续追问 5 层"为什么"，直到触及根本问题：

```
需求："用户想要一个导出报表功能"

Why 1: 为什么需要导出？→ "想用Excel做数据分析"
Why 2: 为什么不在系统里分析？→ "系统里的图表不够灵活"
Why 3: 为什么不够灵活？→ "不能自定义维度和指标"
Why 4: 为什么需要自定义？→ "不同部门关心的数据维度不同"
Why 5: 为什么不用BI工具？→ "没用过，不知道能不能接"

→ 真正需求：灵活的多维数据分析能力，导出只是手段
→ 替代方案：对接BI工具 / 增强系统内报表的自定义能力
```

### 2.2 多视角审视

从至少 3 个视角审视需求（详见 `references/perspectives.md`）：

| 视角        | 核心问题                                     |
| ----------- | -------------------------------------------- |
| 👤 用户视角 | 用户真正要完成什么任务？使用频率？学习成本？ |
| 💼 业务视角 | 商业价值是什么？ROI？与战略目标的关系？      |
| 🔧 技术视角 | 技术可行性？与现有架构的契合度？技术债？     |
| 🎨 体验视角 | 当前体验的痛点？期望体验的关键时刻？         |
| 📊 数据视角 | 需要什么数据？数据从哪里来？数据质量？       |
| 🔒 安全视角 | 权限控制？数据敏感性？合规要求？             |

### 2.3 场景穷举

用给定-当-则（Given-When-Then）格式穷举场景：

```
正常场景（Happy Path）：
  给定 用户已登录且有权限
  当 用户执行核心操作
  则 系统返回预期结果

边界场景（Edge Cases）：
  给定 用户输入了极端值/空值/超长值
  当 用户提交
  则 系统给出明确提示而非崩溃

异常场景（Error Cases）：
  给定 网络中断/服务超时
  当 用户操作到一半
  则 数据不丢失，可恢复

并发场景：
  给定 两个用户同时编辑同一数据
  当 双方都点击保存
  则 后保存者收到冲突提示

权限场景：
  给定 无权限用户
  当 尝试访问该功能
  则 明确的权限提示
```

> 完成播报：`"✅ Step 2 发散展开完成：5Why追溯到根因 / {N}个视角 / {N}个场景"` — 至少覆盖正常+边界+异常 3 类场景。
>
> **验证检查点：**
> ```
> □ 5Why 追溯 ≥ 3 层（理想 5 层）
> □ 至少 3 个视角审视（含安全视角）
> □ 至少覆盖正常+边界+异常 3 类场景
> □ 已调用 references 文档（如需要）
> ```

## Step 3 — 评估收敛 [中自由度 · 强制]

> **不是所有想法都值得做，不是所有需求都要满足。诚实地评估。**
>
> 自由度说明：价值验证矩阵是固定的，但假设审计的深度和可行性判定的具体标准可根据需求复杂度调整。

### 3.1 价值验证矩阵

| 维度         | 评分(1-5) | 说明                                             |
| ------------ | --------- | ------------------------------------------------ |
| 用户痛点强度 | ?/5       | 1=锦上添花 5=切肤之痛                            |
| 影响用户范围 | ?/5       | 1=个别人 5=几乎所有用户                          |
| 使用频率     | ?/5       | 1=每年几次 5=每天多次                            |
| 商业价值     | ?/5       | 1=无直接价值 5=核心收入驱动                      |
| 战略契合度   | ?/5       | 1=与战略无关 5=战略级项目                        |
| **综合得分** | ?/25      | **≥18 强烈建议做 / 12-17 视资源决定 / <12 暂缓** |

### 3.2 假设审计（强制）

> **隐藏假设是需求失败的 #1 原因。必须审计！**

```
【必须为真】（错了整个需求就死）：
  □ 假设1: {描述} → 验证方式: {如何验证}
  □ 假设2: {描述} → 验证方式: {如何验证}

【应该为真】（错了需要调整方案但不至于死）：
  □ 假设1: {描述} → 降级方案: {如果错了怎么办}

【可能为真】（次要假设，影响优化方向）：
  □ 假设1: {描述}
```

### 3.3 可行性速判

| 信号               | 判定        | 行动                   |
| ------------------ | ----------- | ---------------------- |
| 技术上不可行       | 🛑 直接标记 | 告知用户，建议替代方案 |
| 依赖外部系统未就绪 | 🟡 高风险   | 明确前置条件           |
| 与现有架构冲突     | 🟡 高风险   | 评估重构成本           |
| 需要特殊技能/资源  | 🟡 中风险   | 明确人力需求           |
| 所有条件就绪       | 🟢 可行     | 进入 Step 4            |

> 完成播报：`"✅ Step 3 评估收敛完成：价值 {N}/25 / {N}个假设已审计 / 可行性 {结论}"`
>
> **验证检查点：**
> ```
> □ 价值矩阵 5 维度均已评分
> □ 假设审计覆盖 3 个级别（🔴🟡🟢）
> □ 可行性已有明确结论（可行/高风险/不可行）
> ```

## Step 4 — 优先级排序 [低自由度 · 强制]

> 自由度说明：MVP 定义和优先级排列必须严格按 MoSCoW 框架执行，不允许自由发挥。

> **MVP 的定义不是"最少做多少"，而是"最少验证什么"。**

### 4.1 MoSCoW 优先级

```
🔴 Must Have（必须有 — 没有则产品不可用）：
  - {需求项} — 理由: {为什么是必须的}

🟡 Should Have（应该有 — 重要但可延后）：
  - {需求项} — 理由: {为什么重要但可延后}

🟢 Could Have（可以有 — 锦上添花）：
  - {需求项} — 理由: {为什么不急}

⚪ Won't Have（不做 — 明确排除）：
  - {需求项} — 理由: {为什么不做的决策依据}
```

### 4.2 边界约束

```
✅ 范围内（In Scope）：
  - {明确要做的}

❌ 范围外（Out of Scope）：
  - {明确不做的}
  - 理由：{为什么不做的决策}

⚠️ 待定（Deferred）：
  - {需要更多信息才能决定的}
  - 阻塞原因：{缺什么信息}
```

### 4.3 依赖与风险

```
📎 前置依赖：
  - {依赖项} → 负责人/团队 → 预计就绪时间

🚨 已识别风险：
  - 风险: {描述}
  - 影响: {高/中/低} 概率: {高/中/低}
  - 缓解: {应对措施}
```

> 完成播报：`"✅ Step 4 优先级排序完成：M:{N} S:{N} C:{N} W:{N}"`
>
> **验证检查点：**
> ```
> □ MoSCoW 四级分类完整（含 Won't Have 理由）
> □ In/Out of Scope 边界明确
> □ 依赖与风险已登记
> ```

## Step 5 — 交付验证 [低自由度 · 强制]

### 5.1 产出结构化需求文档

使用 `references/output-template.md` 中的完整模板输出需求文档（含概述 → 需求详情 → 验收标准 → 边界约束 → 风险假设 → 价值评估 6 个章节）。

```
□ 需求描述可被一个不了解背景的人看懂
□ 所有验收标准具体可测试（无"体验好""性能快"等模糊词）
□ 所有 5Why 追溯到根本原因
□ 假设已审计并附验证方式
□ 边界明确（做什么 + 不做什么）
□ MoSCoW 优先级有决策理由
□ 风险已识别并附缓解措施
□ 依赖项已明确负责人和时间
□ 文档格式完整，无空白章节
```

> 完成播报：`"✅ Step 5 交付验证完成：文档已产出 / {N}/{8} 项验证通过"`

## 反模式清单

| 反模式                         | 正确做法                              |
| ------------------------------ | ------------------------------------- |
| 用户说"做个导出"就直接设计方案 | 5Why 追溯到真正需求                   |
| 只考虑 Happy Path              | 穷举边界 + 异常 + 并发 + 权限场景     |
| 跳过假设审计                   | 每个需求至少审计 3 个"必须为真"的假设 |
| "先做出来看看效果"             | 定义可测试的验收标准                  |
| 不区分优先级全部列入           | MoSCoW 分级，明确 Won't Have          |
| 忽略安全/权限视角              | Step 2 多视角审视必须包含安全视角     |
| 把用户的原话当需求             | 区分"用户说的"vs"用户需要的"          |
| 一次追问过多问题               | 每轮 3-5 个关键问题，分批深入         |
| 价值评分时过于乐观             | 以数据为依据，不凭感觉打分            |

## 错误处理

| 错误场景                 | 处理方式                       |
| ------------------------ | ------------------------------ |
| 用户无法说清目标用户     | 给出 3-5 个常见角色供选择      |
| 需求过于庞大无法一次澄清 | 拆分需求域，每次聚焦一个子域   |
| 用户要求跳过某些步骤     | 说明跳过的风险，记录跳过声明   |
| 需求在不断变化           | 锁定当前版本号，标记为"进行中" |
| 用户拒绝做价值评分       | 用"不做这个功能会怎样"反推价值 |
