# 假设审计方法论

> **隐藏假设是需求失败的 #1 原因。** 每个需求背后都有大量未经检验的假设。这些假设如同地基——如果地基有裂缝，楼盖得再漂亮也会塌。

## 为什么要审计假设

1. **假设 = 风险**：每个未验证的假设都是一个潜在的失败点
2. **假设有层级**：有些假设错了整个需求死，有些只是影响优化方向
3. **假设会传染**：一个错误假设会导致一连串错误决策
4. **确认偏误**：人们倾向于寻找支持自己假设的证据，而非挑战它

## 假设分级体系

### 🔴 一级假设（Dealbreaker — 必须为真）

> 如果这个假设是错的，整个需求/产品就不成立。

**特征**：

- 直接决定需求的存在价值
- 无法通过调整方案来绕过
- 验证成本通常不高（因为不会被做，一旦错了就止损）

**典型例子**：

```
- "用户愿意为这个功能付费" → 如果用户不愿意，商业模式不成立
- "目标用户有这个痛点" → 如果用户感受不到痛，不需要解决方案
- "监管允许我们收集这个数据" → 如果违规，功能不能上线
- "第三方API提供我们需要的字段" → 如果没有，核心能力缺失
```

**验证义务**：必须在开发前验证。验证方式要具体可执行。

### 🟡 二级假设（Should Hold — 应该为真）

> 如果错了，需求方向需要调整，但不至于全盘推翻。

**特征**：

- 影响方案设计和优先级
- 错了需要 A/B 方案切换
- 验证成本中等

**典型例子**：

```
- "用户更偏好自助操作而非人工服务" → 如果错了，交互模式需要改变
- "数据更新频率可以接受 T+1" → 如果用户需要实时，架构需要调整
- "单页应用能满足性能要求" → 如果不行，需要SSR或其他方案
```

**验证义务**：需要有降级方案（Plan B）。尽早低成本验证。

### 🟢 三级假设（Nice to Have — 可能为真）

> 影响体验优化方向，但不影响核心逻辑。

**特征**：

- 主要影响非核心体验
- 可以在上线后通过数据验证
- 验证成本低或在自然使用中会暴露

**典型例子**：

```
- "用户会使用快捷键提高效率" → 没快捷键不影响可用性
- "夜间模式会有10%用户使用" → 没夜间模式不影响核心功能
- "用户会分享结果到社交网络" → 不分享也不影响工具价值
```

**验证义务**：记录即可，上线后通过数据观察。

## 假设审计模板

对每个需求，逐项列出并分级：

```markdown
## 假设审计：[需求名称]

### 🔴 一级假设（Dealbreaker）

| #   | 假设       | 为什么是这个级别     | 验证方式         | 验证成本   |
| --- | ---------- | -------------------- | ---------------- | ---------- |
| 1   | {假设内容} | {如果错了会发生什么} | {低成本验证方法} | {低/中/高} |
| 2   | ...        | ...                  | ...              | ...        |

### 🟡 二级假设（Should Hold）

| #   | 假设       | 为什么是这个级别 | 降级方案（Plan B） |
| --- | ---------- | ---------------- | ------------------ |
| 1   | {假设内容} | {错了的影响}     | {如果错了怎么办}   |
| 2   | ...        | ...              | ...                |

### 🟢 三级假设（Nice to Have）

| #   | 假设       | 验证时机              |
| --- | ---------- | --------------------- |
| 1   | {假设内容} | 上线后/灰度期/A/B测试 |
| 2   | ...        | ...                   |

### 审计结论

- 一级假设：{N} 个 → 需在开发前验证 {N} 个
- 二级假设：{N} 个 → 已准备降级方案 {N} 个
- 三级假设：{N} 个 → 上线后观察
- 🚨 风险提示：{如果有高风险未验证的一级假设，在此预警}
```

## 假设挖掘技巧

### 从需求描述中提取隐含假设

| 需求描述                 | 隐含假设             | 挑战问题                         |
| ------------------------ | -------------------- | -------------------------------- |
| "用户点击按钮后看到报表" | 用户知道按钮在哪     | 按钮位置是否显而易见？           |
| "系统自动发送通知"       | 用户想要收到通知     | 通知频率是否骚扰？用户能否关闭？ |
| "管理员可以配置规则"     | 管理员理解规则的含义 | 配置界面是否足够直观？           |
| "数据实时更新"           | 实时是必要的         | T+1能满足需求吗？                |
| "支持所有浏览器"         | 所有浏览器都很重要   | 实际用户用什么浏览器？           |

### 从"为什么"挖掘

对每个关键决策追问：

```
决策：我们选择使用 WebSocket 实现实时推送

Why 1: 为什么需要实时？→ "用户需要立即看到新消息"
Why 2: 为什么不能轮询？→ "轮询有延迟，用户体验差"
Why 3: 延迟 3 秒可以接受吗？→ "即时通讯场景不行，但通知可以"
→ 假设：用户对"即时"的定义是秒级而不是毫秒级
→ 验证：做一个 3 秒轮询的原型，测试用户是否察觉
```

### 常见漏审假设速查

```
□ 用户知道这个功能存在（可发现性）
□ 用户理解这个功能怎么用（可学习性）
□ 用户愿意改变现有习惯（行为改变）
□ 数据质量和完整性足够支撑需求
□ 第三方服务的SLA能匹配我们的要求
□ 性能在峰值流量下不会降级
□ 用户设备/浏览器支持所需特性
□ 用户有稳定的网络连接
□ 用户会主动提供我们需要的输入
□ 安全合规不会在未来收紧
```
